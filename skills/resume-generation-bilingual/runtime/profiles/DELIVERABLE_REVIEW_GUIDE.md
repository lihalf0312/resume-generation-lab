# 完整交付对象的源审与一致性审核

这份指导用于新的产品候选。生成仍采用原受控生成结构；完整源审另建投影，不改变旧批请求、响应或账本。来源事实和JD要求始终分开。

## 必须覆盖

逐项读取姓名、所有大栏/学校/公司/岗位/项目标题、日期、正文、独立概括标签，以及 selection_notes、necessary_questions、optional_questions、state。纯问题或中性标题也必须有明确判断，不能因为“非正文”跳过。问题中隐含的日期、身份、缺失能力等前提需要核源。

每项检查施事者、动作、阶段/状态、数字及其计数载体、时间、能力/资格、归属语境。团队/同伴动作不能变成本人；批准构建、批准措辞和批准发送不是同一对象；交接包的并列材料不能搬进某张清单。未提供资格、未申报技能不证明没有资格或能力。未知活动性质不得猜成有偿实习、志愿者或领导。

保持判断强度：矛盾、无据强化、源文歧义、合理省略、notes单独失真、文字精度和展示偏好分开。不对 Proficient/熟练作全局关键词封禁；已有实际工具用途是能力证据，是否概括过强需结合范围，而非自动等同虚构母语或头衔。

## 正文与辅助文字互查

说明声称“保留”的事实必须在实际正文中存在；说“省略”的不能仍出现在正文。必要追问和 awaiting_user 不会让正文擅选的冲突月份获得依据。允许只展示已确认结束期，并在必要问题中保留真实冲突。可选问题不自动阻塞安全草稿，问题本身不能捏造“未来日期”等前提。

只使用明确传入的 runtime_date_basis 比较日历。未知时不猜当前日期；只有月份时不猜具体日。日历位置不能推导在读、毕业、授位或完成状态。文本候选中自称版式、尾行或视觉通过没有实际观测支持，不算验收证据。

## 软件边界

build_deliverable 对原始文档和完整 generation 做精确匹配，建立覆盖全部字段的版本。正文节点保留稳定ID；标签有独立ID；辅助文字按所属字段、完整文本及重复序号生成稳定ID，原文不变的重排或正文修订保留ID，改文生成新ID。任何正文、标签、辅助文字、来源或时钟变化都会使旧审核凭证失效。

build_review_request 带完整源块、整个交付对象、当前时钟依据和所需全部ID。audit_review 验证每个ID恰好一次、文本哈希、来源和时钟链；既核 source_judgment 又核 context_consistency。漏审、负面或歧义只阻止当前对象最终通过，不阻止preview或其他案例。passed表示审核声明无未决项；delivery_ready还要求没有必要问题且state为ready。

引用定位只能证明引文在原文某处，不证明蕴含或真实性。正文/身份日期个人支持不能用JD替代。纯标题和问题的non_assertive是审核者的语义判断，不是程序凭关键词自动豁免；任何支持声明仍不是自动事实真理。

apply_auxiliary_patch 仅接受稳定ID、原文哈希、来源引用和原因的replace/delete；不能借此改正文或静默删state。更新必要问题也要重新完整审核。正文patch后必须用实际新正文重新建立generation.resume和完整投影，旧notes不能假装已经重新核过。

开发fixtures中的真实失败摘录与编辑判断只用于离线回归，不进入生成指导、生成输入或独立评审提示。这次软件验证不等于新模型质量已提高，仍需未来另获授权的真实模型验证。

完整版本另绑定实际加载的审核模块、审核 schema 与实际审核指导。代码、schema 或指导变更必须重建投影和重新审核，文字未变也不能复用旧 receipt。文档已有 intent_context 时必须与同一 JD 一致；旧文档没有该字段不据此拒绝。
